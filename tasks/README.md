# タスクセットの書き方

`tasks/*.yml` に配列で定義する。ファイルはカテゴリごとに分けると管理しやすい。

```yaml
- id: concept-001            # 一意。カテゴリ接頭辞 + 連番
  category: concept          # 下記カテゴリのいずれか
  audience: "..."            # 想定読者。評価対象モデルにも採点器にも渡す
  tags: [k8s, beginner]      # 絞り込み用の任意ラベル
  constraints:
    max_chars: 1200          # 任意。指定すると生成プロンプトに制約として付く
  prompt: |                  # 評価対象モデルへの指示
    ...
  must_cover:                # 採点器だけが見る「必ず触れるべき要点」。網羅性の判定に使う
    - "..."
```

## カテゴリ

| category | 内容 | 読みやすさで差が出やすい点 |
|---|---|---|
| concept | 概念・仕組みの説明 | 前提知識の飛躍、抽象と具体の順序 |
| procedure | 手順書・セットアップ | 手順の粒度、前提条件の明示、確認方法 |
| troubleshoot | エラー・障害の切り分け | 原因候補の整理、確認順序 |
| design | 設計判断・トレードオフの説明 | 比較軸の明示、結論の位置 |
| error_message | エラーメッセージの解説 | 原因と対処の分離 |
| review | コードレビューコメント | 指摘の根拠、修正案の具体性 |
| rewrite | 既存文書の書き直し | 元の情報を落とさずに整理できるか |

## 作るときの注意

- `must_cover` は「読みやすさ」ではなく「落としてはいけない情報」を書く。短くして読みやすく見せる出力を検知するためのもの。文言一致ではなく採点器が意味で判定する。
- 正解が一つに定まる問題(計算、事実の暗記)は避ける。読みやすさの差が出ない。
- 公開するセットと、手元に残す検証用セットを分ける。学習データへの混入を避けるため。
- 1カテゴリ15〜40件、合計100〜300件を目安にする。現在は各カテゴリ15件、計105件が入っている。
